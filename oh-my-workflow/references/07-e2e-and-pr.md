# 验收、走读、开 PR

在所有开发阶段（和大档终审）收口之后做。顺序固定：E2E → `pr-walkthrough` → 开 PR。走读没完成不准开 PR。

## 端到端验收

前置：全仓 check 绿。按项目的方式把应用真跑起来。路径清单从执行计划的阶段目标反推，不是把整个产品重走一遍。

对每条路径真实操作一遍并截图：功能是否真的发生；空状态 / 加载中 / 错误态 / 长内容截断；i18n 漏翻或裸 key；溢出、错位、间距、可点区域；暗色 / 亮色；键盘能否走完主流程。

**修**（属于本次交付）：明确的展示问题；跟周边组件不一致的间距/圆角/字重，跟既有交互模式冲突的操作。修完重跑 check。UI 修复单独 commit，`fix(ui): …`，并写 runlog。

**不修**（记 follow-up，写进 PR 的已知项）：本次未触达路径上的既有问题；需要重新设计的产品决策；需要新依赖或跨层重构才能解决的。

工具不可用：follow-up，不假装测过。

## 走读

加载同仓库 `pr-walkthrough` skill，**按其 SKILL.md 执行**，不要在这里复述它的步骤。

输入：本次分支相对 `workflow_base_sha` 的 diff（本地 `git diff workflow_base_sha...HEAD`）。这是自己的变更，随附文档在 `.ai_docs/<slug>/`（design / tech-design / plan / runlog）。

`pr-walkthrough` 第零步缺依赖：本流水线停在开 PR 之前，只说缺什么。不提供替代输出，不把「未走读」的 PR 交出去。

走读报告的原文链接（飞书文档 URL 或任何「打开原文」的地址）只出现在编排者对用户的会话回复里。禁止出现在：

- PR 标题、正文、review comment、issue 引用
- commit message
- 将进入该 PR 的任何仓库文件，包括 `.ai_docs/`

会话回复里可以给链接。PR 里最多写一句「已走读」，不附地址。

## 开 PR

一个 PR，标题 ≤ 70 字符。描述里写：

- 变更摘要
- 验证过什么（命令 + E2E 路径；截图挑关键的贴，不要堆）
- 跳过了什么、已知 follow-up（说人话）
- 已走读（无链接，规则同上）

agent 在到达这一步之前不 push、不开 PR。`attended` 把变更文件清单再给用户看一眼再开。
