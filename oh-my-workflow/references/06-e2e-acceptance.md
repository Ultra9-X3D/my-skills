# agent-browser 端到端验收

在所有开发阶段 + review workflow 都收口之后做。这是把 PR 交出去之前的最后一道。

## 前置

1. 全仓 check 绿。
2. 按项目的方式把应用真跑起来（有 `run` 类 skill 就用它；桌面端 / 服务端各按其入口）。
3. 手上要有一份**本次触达的用户路径清单**——从执行计划的阶段目标反推，不是把整个产品重走一遍。

## 走查内容

对每条路径，真实操作一遍并截图：

- **功能对不对** — 本次新增/改动的行为是否真的发生了。
- **状态齐不齐** — 空状态、加载中、错误态、长内容截断。这几个是最常被漏的。
- **文案** — i18n key 有没有漏翻、有没有裸 key 漏出来、中英混排。
- **布局** — 溢出、错位、间距不一致、对齐乱、可点区域太小。
- **暗色 / 亮色** — 两个主题都看。对比度不够的要改。
- **键盘可达** — 焦点顺序、焦点可见、能不能用键盘完成主流程。

## 修什么、不修什么

**修**（属于本次交付）：
- 明确的展示问题：错位、溢出、缺状态、漏翻译、对比度不足、焦点丢失。
- 不和谐的 UI/UX 呈现：跟周边组件不一致的间距/圆角/字重，跟既有交互模式冲突的操作。

**不修**（记下来，写进 PR 描述的"已知项"）：
- 本次未触达路径上的既有问题。
- 需要重新设计的产品决策。
- 需要新依赖或跨层重构才能解决的。

修完重跑 check，截图存证。修 UI 的 commit 单独提，`fix(ui): …`。

## 收尾

PR 描述里写：走查了哪些路径、修了哪些展示问题、哪些已知项留着。截图挑关键的贴，不要堆一屏。
