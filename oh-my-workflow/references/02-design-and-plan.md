# design、手书、阶段、执行计划

字段清单在 `01-boot-and-artifacts.md`。这里只写怎么写、怎么切、何时停。

## design 与 tech-design

`design.md` 给人。`tech-design.md` 给实现 agent。后者必须自包含：把开工需要的决策抄进来，禁止「见 design.md」「如上文」。

现状代码只贴亲手读过的，给到文件路径，不贴行号。契约写成签名和存储形状，不写成散文。

`attended` 时 design 是卡口：只交 design（含阶段草案），等认可。不要在同一条消息里连带执行计划。

## 什么叫自包含（plan 与 tech-design 共用）

读它的人（和 agent）不需要打开任何其它计划文档就能开工。

禁止：引用别的执行计划、引用会话历史、只给链接不给内容。需要的规则原文抄进来。

允许：引用仓库里的长期文档（`AGENTS.md`、`docs/*`）和具体代码路径。

## 切阶段

按**依赖方向**切，不按文件目录切。一个阶段的产物是下一个阶段的输入，阶段之间不能互相等待。stage 数量上限以 SKILL.md 分档表为准。

典型的四段形状（不是模板，是常见解）：

1. **契约与数据层** — schema / migration / API 契约 / 类型 / 事件信封。
2. **服务端实现** — 契约落地 + 单测 / 集成测试。
3. **客户端接入** — 消费契约的 UI / CLI。
4. **收口** — i18n、文档、边界检查、跨层清理。

需求天然只有两三段就写两三段。不要为了凑满上限而制造假阶段。一个 stage 若只剩两三个小 commit，合并进相邻 stage。

每个阶段必须写清：目标（完成后系统能做什么）、触达范围（包 / 目录）、commit 列表、可执行的完成判据、不做什么。

装不进该档上限：停下问用户是否另开 PR。不准加 stage，不准把超额工作藏进「再拆几个 agent」。

## commit 粒度

切 commit 的可观察标准：范围 + 完成标准能写进**一条** prompt。写不进就再拆。

- 一个 commit = 一个可独立解释的变更。
- 稳定 id：`sN-cM`（如 `s1-c2`）。
- schema / migration 单独成 commit，跟消费它的代码分开。
- 纯机械改名、格式化、依赖 bump 单独成 commit。
- 测试跟被测代码同 commit。不要留「后面补测试」。

## 单 agent 预算（300k）

单个 agent 要能在 300k 内读完 + 改完 + 验完。粗算：

- 读一个中等文件 ≈ 3~8k；读一个大文件（>800 行）≈ 15~30k。
- 一次完整 typecheck + test 输出（有失败时）≈ 10~40k。
- 修 → 验 → 再修的循环，按 3 轮预留。

合理上限：**触达 8~15 个文件，其中深读 5 个以内**。超了就拆成下一笔 commit，或在文件不重叠时并行（见 `03-workflow-authoring.md`）。不要用加 stage 来消化。

## 交给用户审批的阶段草案

紧凑表，不要实现细节、不要贴代码：

```
阶段 1｜<名字>
  目标：…
  范围：packages/api, packages/db
  commits：
    - feat(db): …
    - feat(api): …
  判据：<仓库 typecheck / test 命令> 全绿
  不做：UI 接入（阶段 3）
```

结尾问：这个划分认可吗？认可再写出自包含的执行计划。

## 执行计划

用 `assets/execution-plan.template.md`。必备：背景与非目标、已读代码事实、总体设计与决策、阶段拆分（含 `plan_item_id` 与允许路径）、执行方式、从 `04-agent-briefing.md` 粘贴的 BRIEFING 原文、整体完成判据、风险与假设。

简体中文散文；路径 / 标识符 / 命令保持英文。判据是能粘进终端的命令。
