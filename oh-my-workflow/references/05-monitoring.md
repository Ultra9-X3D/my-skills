# 无人值守监控

用户在第一个 workflow 开跑后就离开了。从那一刻起，判定和决策都归你。

## 基本节奏

- workflow 在后台跑，完成时来 `<task-notification>`。**不要轮询**，也不要为了等它 sleep。
- 收到通知先读结构化结果（verify agent 的 schema 输出），再决定下一步。
- 串行推进阶段：上一阶段门禁绿了才起下一个。别为了省时间提前起。
- 阶段之间自己跑一次快速确认：`git log --oneline`、`git status`、跑一次全仓 check。别只信 agent 的自述。

## 判定规则

| 情况 | 做法 |
| --- | --- |
| 门禁全绿 | 直接推进下一阶段，不用问 |
| 少量测试失败、原因清楚 | 自己修或派一个 fix agent 修，然后重跑门禁 |
| 同一处失败修了 2 次还在 | 停止增量微调。诊断根因，换一条路，说清换了什么 |
| agent 报告与实际 git 状态不符 | 信 git。以实际 diff 为准重新判定 |
| 需要偏离用户已认可的阶段划分 | 只要不缩减范围就自己决定并记录；缩范围要等用户 |
| 需要做破坏性操作（删多文件、force push、改 CI/生产配置）| 停下来等用户 |
| 阶段范围明显估错、装不进 300k | 在阶段内往下拆 agent 重跑该阶段，不要加阶段 |

## 需要 escalate 的（用 PushNotification，一句话说清可行动的事实）

- 出现需要用户拍板的方向性分歧。
- 门禁在换过路子之后仍然不绿。
- 需要破坏性或对外操作。
- 全部完成、PR 已开。

不要为常规进度发通知。用户走了，不代表想被每个阶段打断。

## 记录

每阶段结束在会话里写一段简短结论：这阶段做完了什么、门禁结果、有什么未解决项被推到后面。用户回来要靠这个补齐上下文。

发现值得跨会话留存的事实（工具坑、命令替代、项目约束），写进 memory；只跟本次会话有关的不写。
