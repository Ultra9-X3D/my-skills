# 无人值守监控

用户在第一个 workflow 开跑后就离开了。从那一刻起，判定和决策都归你。走读与开 PR 的步骤本身见 `07-e2e-and-pr.md`。

## 基本节奏

- workflow 在后台跑，完成时来通知。**不要轮询**，也不要为了等它 sleep。
- 收到通知先读结构化结果和磁盘上的 runlog / 审查文件，再决定下一步。pane 或返回值与文件矛盾时，以仓库代码和磁盘文件为准。
- 串行推进阶段：上一阶段门禁绿了才起下一个。
- 阶段之间自己跑一次快速确认：`git log --oneline`、`git status`、跑一次全仓 check。别只信 agent 的自述。

## 判定

| 情况 | 做法 |
| --- | --- |
| `halt` 为空且 `converged=true` | 推进下一阶段，不用问 |
| `halt=finding-explosion` | 停。把两轮 finding 摊给用户。禁止再派 fix |
| `halt=implement-blocked` / `verify-red` / `gate-red-no-next-round` | 停。按返回值升级。脚本内已修过门禁，编排器不要另开一轮「再试试」 |
| agent 报告与实际 git 状态不符 | 信 git |
| 需要偏离已认可的阶段划分（扩或缩） | 停下来等用户（attended）或升级（unattended） |
| 需要破坏性操作（删多文件、force push、改 CI/生产配置） | 停下来等用户 |
| 阶段范围明显估错、装不进单 agent 预算 | 拆 commit 写进 CONFIG 后重跑该 stage 脚本，不要加 stage |
| 审查产物文件缺失 | 记 follow-up，不要用编排者文字填空 |

## 编排者禁区

- 不得给吸收清单增删条目。
- 不得用自己的意见顶上失败的审查。
- 不得合别人的分支。
- 走读与开 PR 的禁令见 `07-e2e-and-pr.md`。

## 需要升级的（一句话说清可行动的事实）

- 出现需要用户拍板的方向性分歧，或要改范围。
- 门禁在换过路子之后仍然不绿。
- 需要破坏性或对外操作。
- 走读依赖缺失，PR 开不了。
- workflow 返回 `halt`（含 `finding-explosion`）。
- 全部完成、PR 已开。

不要为常规进度发通知。

## 记录

每阶段结束写 `runlog/s<NN>-status.md`，并在会话里留一段短结论：做完了什么、门禁结果、未解决项。用户回来靠这个补上下文。

只跟本次会话有关的不写进长期 memory；跨会话仍成立的工具坑、命令替代、项目约束才写。
