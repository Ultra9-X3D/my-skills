# Agent Briefing（强制内联）

下面这段是**每个 agent prompt 的第一段，逐字内联，不改写、不摘要、不用"见上文"替代**。子 agent 不继承主会话上下文，省掉这段等于没说过。

---

## BRIEFING（原文）

```
【项目阶段】
我们现在处于内部开发阶段，没有真实用户，没有需要保护的线上数据，没有向后兼容负担。

【这意味着什么】
任何不是最佳实践的代码实现和架构设计，都会在后面造成巨大影响。所以：

- 不要为了兼容现有设计而妥协。现有代码写得不对就改它，不要在它旁边加一层适配。
- 尽可能往最佳实践靠齐。命名、分层、依赖方向、错误处理、类型精度，都按你认为对的做。
- 允许抽出公共部分、允许重构、允许删除。发现重复实现就合并，发现死代码就删掉。
- 但不要过度设计。不要为了假想的扩展点加抽象层，不要为了"以后可能要换实现"加接口。
- 不要提前过度防御。不要给不可能发生的输入加校验，不要为极端 corner case 加分支。
  过多的防御性代码和 corner case 处理，反倒是后续架构优化的负担 —— 它让人不敢改。

【判断标准】
问自己：如果这段代码的作者三个月后要重构它，我现在写的东西是帮他还是拖累他？
帮他的：清晰的分层、准确的类型、去掉的重复。
拖累他的：多余的抽象、防御性分支、为兼容旧写法留的双路径。

【风格】
读周边代码再写代码。注释密度、命名习惯、惯用法都跟着现有代码走，不要引入新的库或新的模式除非确有必要。
```

---

## 除 briefing 之外，每个 agent prompt 还必须带

1. **本 agent 的具体任务** — 目标 + 触达范围 + 明确的不做什么。
2. **需要的现状事实** — 已知的文件路径与结论，省掉重复探索。
3. **完成判据** — 具体命令。
4. **提交要求** — commit message 格式；说明所有 commit 都落在同一个分支上，不要建分支、不要提 PR、不要 push。
5. **返回什么** — 说明"你的最终文本就是返回值"，要结构化事实（改了什么、判据结果、未解决项），不要写给人看的寒暄。

## 模板

```ts
const BRIEFING = `【项目阶段】
我们现在处于内部开发阶段，没有真实用户……
（此处必须是上面 BRIEFING 的完整原文）`

const prompt = `${BRIEFING}

【你的任务】
…

【现状（已确认，无需重新探索）】
…

【不要做】
…

【完成判据】
…

【提交】
在当前 worktree 的当前分支上提交，commit message 用 \`type(scope): subject\`。
不要创建分支，不要 push，不要开 PR。

【返回】
你的最终文本就是返回值。返回：改动的文件清单、每条 commit 的 sha 与 subject、
判据命令的实际输出结论、以及任何你没能解决的问题（明确说清，不要粉饰）。`
```
