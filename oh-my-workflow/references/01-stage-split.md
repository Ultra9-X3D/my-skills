# 阶段划分与 commit 拆分

## 切阶段的依据

按**依赖方向**切，不按文件目录切。一个阶段的产物是下一个阶段的输入，阶段之间不能互相等待。

典型的四段形状（不是模板，是常见解）：

1. **契约与数据层** — schema / migration / API 契约 / 类型 / 事件信封。下游全靠它，先冻结。
2. **服务端实现** — 契约的落地实现 + 单测 / 集成测试。
3. **客户端接入** — 消费契约的 UI / CLI，含状态与交互。
4. **收口** — i18n、文档、边界检查脚本、跨层清理与去重。

如果需求天然只有两三段，就写两三段。**不要为了凑满 4 段而制造假阶段。**

## 每个阶段必须写清

- **目标**：一句话，说完成后系统能做什么（不是"改了哪些文件"）。
- **触达范围**：具体到包 / 目录，越窄越好。
- **commit 列表**：每个 commit 一行，`type(scope): subject` + 一句内容说明。commit 数量不限。
- **完成判据**：可执行的命令 + 期望结果。含仓库自带的 check 脚本。
- **不做什么**：明确划到后续阶段的东西，防止 agent 越界扩张。

## commit 粒度

- 一个 commit = 一个可独立解释的变更。能一句话说完就行，不必强求可单独回滚。
- schema/migration 单独成 commit，跟消费它的代码分开。
- 纯机械改名、格式化、依赖 bump 单独成 commit，不要混进逻辑变更。
- 测试跟被测代码同 commit。不要留"后面补测试"的 commit。

## 300k context 预算怎么估

单个 agent 的活儿要能在 300k 内读完 + 改完 + 验完。粗算：

- 读一个中等文件 ≈ 3~8k；读一个大文件（>800 行）≈ 15~30k。
- 一次完整 typecheck + test 输出（有失败时）≈ 10~40k。
- 修 → 验 → 再修的循环，按 3 轮预留。

所以一个 agent 的合理上限大约是：**触达 8~15 个文件，其中深读 5 个以内**。超了就在阶段内往下拆 agent（用 `pipeline` 或 `parallel`），而不是加阶段。

拆 agent 时优先按**文件不重叠**切分——重叠的写入必须串行，或者给 `isolation: 'worktree'`（贵，仅在真会冲突时用）。

## 交给用户审批的格式

给一张紧凑的表 + 每阶段的 commit 列表。不要在这一步写实现细节、不要贴代码。

```
阶段 1｜<名字>
  目标：…
  范围：packages/api, packages/db
  commits：
    - feat(db): …
    - feat(api): …
  判据：bun run typecheck && bun run test --filter @buffin/api 全绿
  不做：UI 接入（阶段 3）
```

结尾问一句：这个划分认可吗？认可我再出自包含的执行计划。**不要在同一条消息里连带把执行计划也写了。**
